## Query structure and observation channel

SQL injection occurs when untrusted input changes the structure or meaning of a database query. Mapping a parameter is reconnaissance; malformed-input errors are a lead; reproducible query alteration is stronger evidence. Record the DBMS, driver, statement context, privileges and control responses before drawing an impact conclusion.

| Technique | Observation or mechanism | Distinguishing condition |
| --- | --- | --- |
| Tautology | A true predicate changes query logic | Exact string/numeric context must parse |
| Boolean blind | Stable true/false response differences | No direct row/error output required |
| Time-based blind | Conditional delay/work changes timing | Compare controls and baseline jitter |
| Error-based | Deliberately induced errors disclose data/structure | Error content supplies the channel |
| UNION | Additional selected rows join visible output | Compatible columns/types and visible result |
| Stacked/piggybacked | A second statement executes | Driver/DBMS must allow multiple statements |
| Second-order | Stored input becomes unsafe query text later | Delayed execution is the key distinction |
| Out-of-band | Database initiates another communication | Requires reachable supported feature/channel |

A single quote does not itself form a tautology. The source contains corrupt quote/comment examples that should remain transcription evidence. WAITFOR DELAY is Transact-SQL, not an Oracle delay primitive. BENCHMARK, SLEEP and expensive-query constructions are DBMS/version-dependent. Timing alone does not prove whether a deliberate sleep or heavy computation caused it.

## Filter evasion and repair

Whitespace, comments, encodings, parameter handling and concatenation can expose disagreements between filter parsing and backend parsing. Splitting SELECT into SE LECT is not generally valid SQL. A changed representation must still parse under the target DBMS before it can be called a successful bypass. Client-side restrictions do not define the server's query boundary.

Use prepared statements/bound parameters for values. Dynamic identifiers need safe allowlisting/design because binding a value cannot safely substitute arbitrary SQL syntax. Escaping is context/encoding-dependent and is a weaker universal prescription. Database least privilege reduces impact but does not remove the injection. A WAF supplies additional coverage rather than the main query/data boundary.

Example: a stored notification template is harmless when saved but is later concatenated into a scheduled report query. This is second-order injection. Repeat the safe controlled comparison at both the storage and later execution stages; do not use deletion of a real table as the validation method.
