## Session lifecycle and authorization

Authentication establishes an identity; a session token represents continuing state; authorization decides which resources/actions that identity may use. A session can be stolen without learning a password, and a valid session can still be denied access to another user's object. Encryption, MFA and a WAF cover particular paths rather than prove that every session property is secure.

| Mechanism | Defining condition | Matching control |
| --- | --- | --- |
| Fixation | Attacker-known/chosen identifier survives victim login | Rotate on login/privilege change and invalidate old state |
| Replay/sidejacking | Captured valid token is accepted again | Protect transport/storage, expire/revoke state, consider sender/channel binding |
| Prediction | Identifier generation has exploitable patterns or insufficient entropy | Use unpredictable high-entropy tokens |
| CSRF | Victim browser performs an unwanted authenticated action | Anti-CSRF tokens and appropriate origin/SameSite controls |
| MitB | Compromised browser modifies authenticated activity | Endpoint/browser controls and transaction verification |

Logout must invalidate the appropriate server-side session or revoke the token through the system's actual design. A cookie's Secure flag limits transport; HttpOnly blocks ordinary script reads of that cookie but does not neutralize all XSS actions. URLs can leak identifiers through logs/history/referrers. Token length alone does not measure entropy or cipher strength. Expired-token failures followed by a valid-token success do not prove a race.

## Transport-level attacks

TCP injection requires accepted sequence/state conditions. Active hijacking changes the flow; passive capture only observes it. Blind means the attacker cannot observe the relevant flow and must infer/guess state. A forged RST can terminate a connection without transferring it. ARP poisoning requires a local-link position; it is not a universal remote-session attack.

The source repeatedly asks which technique bypasses HTTPS/MFA without alerts while omitting the actual weakness. Hold those keys. A browser zero-day, compromised CA, deserialization defect or predictable token cannot be inferred from the existence of defenses.

Example: a session value introduced before login remains accepted afterward. That supports fixation risk and a rotation test. If the value was instead stolen after login, replay is the correct mechanism. Identical outcomes do not imply identical causes.

## Selected primary checks

- [R12: OWASP: Session Management Cheat Sheet](../references.md#r12): Use unpredictable session identifiers, rotate at authentication/privilege changes and invalidate sessions appropriately; cookie flags cover specific exposure paths.
- [R13: OWASP: CSRF Prevention Cheat Sheet](../references.md#r13): CSRF induces unwanted authenticated requests; origin/token/SameSite controls address that mechanism separately from stealing a session identifier.
