## S01 · Follow the packet

Welcome to Module Eight, Sniffing. Tally returns to Northstar Learning Center with a new question: what can a packet trace actually tell us? Earlier modules discovered hosts, identified services, assessed weaknesses, and examined possible malware behavior. Now we follow communications between those objects. Packet analysis can explain a slow lesson download, an unexpected address change, or a suspicious name response. It can also mislead us when the observation point is wrong. Seeing a packet establishes that the supplied capture contains those bytes. Connecting it to a person, process, successful login, or harmful outcome requires additional evidence. Throughout this lesson, we will name the observation point before interpreting the traffic. We will compare normal mechanisms with possible manipulation, choose a suitable defense, and define a verification check. All Northstar evidence in this package is synthetic teaching material. The offline commands read supplied files; they do not contact the fictional hosts.

## S02 · Capture is an observation

Sniffing means observing network traffic through a capture interface or another collection point. An Ethernet frame carries a network-layer packet, which may carry a transport segment and application data. Each layer answers a different question. A destination MAC address helps deliver a local frame. An IP address identifies a network endpoint in the packet. A TCP port helps distinguish transport conversations. Application data may show a request, but encryption may hide its content. A capture is a sample of what the collection system received and retained. It is not automatically a complete history of the network. A conversation view is an interpretation assembled from that sample. A security conclusion adds another layer of reasoning. Keep these layers separate in your notes. At Northstar, a connection to a classroom service may support troubleshooting. It does not by itself establish which teacher initiated it or whether the service accepted a login.

## S03 · The Northstar traffic map

The teacher laptop, STAFF, keeps its address at ten dot forty-four dot ten dot twenty-one. ANALYST remains the authorized audit workstation. The inherited DNS server remains in the server zone. The shared campus map is unchanged. Module Eight adds an office gateway interface, locally administered teaching MAC addresses, VLAN labels, and DHCP roles in a separate extension. Never infer a direct Ethernet relationship merely because two IP endpoints appear in a conversation list.

## S04 · A bounded collection plan

A useful capture plan begins with a question, such as whether STAFF received competing DNS answers during a known time window. Record the authorized interface, VLAN or segment, permitted devices, duration, retention location, and decision owner. Collect the minimum data needed for that purpose. Even a short capture can contain names, cookies, messages, or other sensitive information. A content filter does not guarantee that every remaining byte is appropriate to disclose. For this package, our executable scope is simpler: read only the supplied synthetic files, preserve their hashes, and record actual tool output. We will not open a live interface, redirect a neighbor's traffic, or start a DHCP service. If future practical training activates a live lab, it needs its own approved environment and acceptance check. Preparing this lesson does not establish that a learner performed such a lab. Keep the collection purpose visible throughout analysis.

## S05 · Ethernet delivers locally

Ethernet uses source and destination MAC addresses to deliver frames on a local link. The EtherType identifies the next protocol, such as IPv4 or ARP. A broadcast destination asks the local broadcast domain to receive the frame. An ordinary unicast destination identifies one link-layer recipient. The MAC address is not a permanent proof of a physical device or a person. Software can change an interface address, virtualization can add interfaces, and operational replacements can change hardware. In our fixtures, every MAC is explicitly assigned for teaching. Read the capture's link type before applying Ethernet assumptions: a file containing another link-layer format may expose different fields. At Northstar, start by identifying the sender, intended local recipient, and carried protocol. Then ask how the receiving switch would forward that frame. That order keeps packet interpretation connected to the actual delivery mechanism instead of a memorized address list.

## S06 · What a switch learns

A learning Ethernet switch associates source MAC addresses with the ports on which it observes them, within the relevant VLAN. It then looks up a frame's destination address to choose a forwarding action. Known unicast traffic normally goes to the learned destination port rather than every access port. Broadcast traffic and some unknown unicast traffic can be flooded within the applicable forwarding domain. Flooding is constrained by VLAN membership, topology, configuration, and device behavior. A switch is therefore not simply a hub with more ports. At Northstar, ANALYST may receive a broadcast ARP request while missing a unicast exchange between STAFF and another device. That difference is expected. It does not show that the capture tool failed. To evaluate a missing packet, ask whether the switch had any reason to deliver it to the observation port. This becomes the foundation for understanding promiscuous mode and monitoring connections.

## S07 · Promiscuous has a boundary

An interface normally filters some received traffic before passing it to the operating system. Promiscuous mode relaxes that local filtering so the capture system can inspect more of the frames delivered to the interface. It does not instruct an upstream switch to copy all other ports. A capture on ANALYST can still miss STAFF's known unicast traffic. Wireless monitor mode is a different capability with adapter, channel, driver, and radio requirements; it is not another name for Ethernet promiscuous mode. This module focuses its executable examples on offline Ethernet files. When someone claims to have captured an entire network by selecting promiscuous mode, ask for the collection topology and switch configuration. At Northstar, document whether the source was an endpoint interface, a configured mirror destination, or a network tap. That evidence determines which missing and present frames are meaningful for the question.

## S08 · Broadcast domains and routes

A VLAN defines a logical Layer Two broadcast domain. A router or Layer Three switch connects IP subnets according to its configuration and forwarding rules. When STAFF sends to an off-subnet DNS server, it normally resolves the office gateway's link-layer address rather than broadcasting ARP for the remote server. The destination IP continues to identify the server while link-layer addresses change across routed links. Broadcasts generally remain within their local domain unless a specific relay or other mechanism handles the relevant protocol. DHCP relay is one such deliberate mechanism; arbitrary Ethernet broadcasts are not simply routed everywhere. In the drawing, trace one packet through the office link and then show the newly framed server-side hop. The gateway and the DNS server play different roles. Keeping those roles explicit prevents an incorrect conclusion that the gateway's MAC address proves the gateway originated the application request.

## S09 · Choose the right evidence

Suppose a teacher says a page loaded slowly. An endpoint capture may show request timing and transport behavior. Switch counters may show congestion or errors. Application logs may show server processing time. None of these sources alone covers every possible cause. Start with the narrow claim you need to test, then identify a collection point capable of observing it. Record what is missing as carefully as what is present. A packet trace does not normally contain the operating system's process identifier; endpoint telemetry is needed for reliable process attribution. Two dashboards based on the same capture are also not two independent observations. At Northstar, our evidence ledger names each source and its limitations. This lets a reviewer distinguish a measured packet count from an inferred explanation. Good analysis reduces uncertainty through the next suitable observation rather than strengthening a conclusion because a diagram looks convincing.

## S10 · Endpoint capture

An endpoint capture is often the easiest place to begin a focused investigation. It can show traffic associated with the host's interfaces, depending on the capture mechanism and privileges. It is also affected by the host's networking stack and offload features. A packet shown with an apparent bad checksum may have been captured before hardware completed the checksum. Segmentation and receive offloads can alter how packet sizes appear at that point. These effects must be checked before declaring corruption or an attack. An endpoint trace can miss traffic on another interface, outside the capture interval, or discarded before the collection hook. At Northstar, label the endpoint, interface, time window, and known offload conditions. Compare suspicious results with a suitable independent observation when necessary. Our synthetic files use explicitly constructed headers and do not simulate a real host's offload pipeline; do not use their clean checksums as proof about a production interface.

## S11 · SPAN copies selected traffic

A switch port analyzer session, often called SPAN or port mirroring, copies selected traffic to a monitoring destination. The selection may involve ports, VLANs, and ingress or egress directions. The monitoring port must be configured for that purpose; plugging ANALYST into an ordinary access port is insufficient. A mirror can also drop copies when selected traffic exceeds destination capacity or device resources. Depending on the platform, tags and timing may differ from the original wire representation. Record the device, session configuration, source directions, destination, and collection interval. A capture file alone rarely proves those settings. In our Northstar visibility example, one file is explicitly labeled as an office endpoint view and another as a fictional mirror view. Their differences are teaching assumptions encoded in the fixture manifest. They illustrate how collection affects evidence, rather than demonstrating that an actual Northstar switch was configured or monitored.

## S12 · A tap has requirements

A network tap provides a dedicated way to observe traffic on a link. Its behavior depends on the medium, design, direction handling, aggregation, and attached capture hardware. Some arrangements deliver each direction separately, while others aggregate them. The collector still needs sufficient capacity and an appropriate link-layer decoder. A tap does not automatically grant visibility into other links, other VLAN paths, or encrypted application content. Installing one on a working network is an operational change with its own authority and availability considerations. For analysis, preserve documentation of the monitored link and how the capture was produced. At Northstar, choosing a tap is a possible future collection design, not an action performed by the package builder. Compare endpoint, mirror, and tap approaches by the specific question and coverage needed. The strongest choice is the one whose documented behavior makes the intended observation possible and whose limitations remain reviewable.

If an expected result differs, retain the original file and command before changing anything. Check the file identity, link type, filter language, and tool version in that order.

## S14 · Two filter languages

A capture filter selects which packets are admitted by the capture mechanism. Libpcap syntax includes expressions such as a host address, an ARP protocol match, or a UDP port condition. A display filter selects which already stored packets the analyzer shows, using decoded protocol fields. Wireshark expressions such as an IP address comparison belong to that second language. The syntax is not interchangeable. A packet excluded during collection cannot be recovered by clearing the display filter. Conversely, hiding a packet in a display does not delete it from the original capture. At Northstar, save the exact expression and whether it was applied during collection or analysis. Our offline tcpdump checks exercise libpcap filtering against files; they do not perform live collection. The Wireshark worksheet supplies separate display expressions. Its documentation review and any actual execution are recorded independently, so a tested capture expression never silently becomes a tested display expression.

## S15 · Read the conversation

Select a conversation by addresses and transport ports, then inspect its packet sequence. For TCP, consider connection establishment, sequence and acknowledgment numbers, payload, and closure. A single packet with a familiar port number does not establish a successful application exchange. A partial capture can begin after establishment or end before a response. UDP has no TCP-style connection handshake, so a request-response relationship requires protocol and transaction context. Our DNS fixture includes identifiers and question names to make that relationship inspectable. Stream reconstruction can help read application data, but missing segments and analyzer assumptions still matter. At Northstar, write the observed request and response separately from any claim of user success. If a synthetic HTTP response contains an ordinary teaching message, that is the content supplied by the fixture. It does not demonstrate a real login, access to a protected account, or traffic intercepted from another person.

## S16 · Missing does not mean absent

A capture's absence of an expected packet supports a limited conclusion: it was not present in the retained data under the recorded collection conditions. The reason could be a genuinely absent exchange, a different route, a filter, a short time window, a collector drop, or truncation. Snapshot length controls how many bytes of each packet are retained. A header may survive while application content is cut off. Capture and interface statistics can help assess loss, but their meaning depends on the tool and collection method. At Northstar, ask whether the sensor could have seen the exchange and whether the stored file is complete enough to answer the question. Record relevant counters and settings when a real lab supplies them. The synthetic fixtures have declared complete record lengths for their constructed packets. That property verifies the fixture format only; it is not evidence that real network collection never loses packets.

## S17 · Plaintext can expose content

Plaintext application traffic can expose request paths, headers, and message bodies to a collector on the communication path. Our HTTP example contains a fictional classroom message with no real account or password. Reading that body demonstrates that those constructed application bytes are visible in the supplied file. It does not establish that a third party's traffic was redirected or that an application accepted a login. HTTP methods also have different meanings: a POST carries a request body but does not automatically mean authentication. Follow the actual message fields and server response rather than guessing from the method alone. At Northstar, use the example to explain why sensitive services need protected transport and careful logging. A capture containing secrets can become a sensitive artifact itself. Keep the original purpose, retention decision, and permitted sharing boundary visible even when analysis tools make content extraction very easy.

## S18 · TLS protects a channel

TLS provides a protected channel when negotiated and authenticated correctly. The handshake establishes parameters and keys, and application records are protected under the resulting state. A passive capture without the necessary secrets generally cannot read that protected application content. Some metadata can remain visible, including IP endpoints, transport information, packet sizes, and timing. Which names or handshake fields are visible depends on the protocol version and deployed features; avoid a universal claim that every destination name is exposed. Proper certificate and hostname validation matter because encryption with an untrusted peer does not establish the intended service identity. At Northstar, compare the readable HTTP teaching message with a clearly labeled conceptual TLS record diagram. We do not supply fabricated TLS bytes as if a real handshake succeeded. Encryption limits payload inspection, while endpoint and service logs may provide other authorized evidence. State which observation supports each conclusion.

## S19 · A VPN has endpoints

A virtual private network can protect traffic across an untrusted path by carrying it inside a protected tunnel. The protection applies between the tunnel endpoints. Traffic before encapsulation or after decapsulation can have a different visibility profile, depending on the original application protocol. An observer outside the tunnel may see outer addresses and timing while losing access to inner content. An observer at an authorized endpoint may have access to additional information. A VPN does not automatically fix an insecure application, a compromised endpoint, or an incorrect trust decision. At Northstar, draw the classroom application path and mark exactly where the tunnel begins and ends. Then ask which segment the sensor observes. This avoids treating a tunnel icon as a universal privacy guarantee. The same reasoning applies when a security device terminates encryption: its authorized role, key custody, logging, and access controls become part of the collection and evidence story.

## S20 · Legacy protocols need context

Some traditional application protocols were designed without modern transport protection. A basic Telnet session can reveal terminal exchanges, and conventional FTP can expose commands and data unless an appropriate protected variant or other protection is used. A port number alone cannot establish which protection is active. Explicit TLS negotiation, alternative transports, tunnels, and nonstandard ports require inspection of the actual protocol and configuration. At Northstar, the legacy device station provides a teaching role for this discussion, while the package supplies only harmless offline text and packets. A defense plan can replace an exposed management path with an authenticated encrypted alternative, restrict who can reach it, and verify that old access paths are actually closed. Keep availability requirements and device capabilities explicit. An inventory entry saying secure management is planned is different from a trace or configuration check demonstrating that the approved protected path is in use.

## S21 · Protection and observation

We can now separate three questions. Was traffic collected at the relevant point? Was its content protected on that path? What authorized evidence can explain application behavior? A capture may answer the first two partly while leaving the third open. Installing a decoder does not create missing encryption secrets, and a packet analyzer does not bypass correct cryptography simply because it recognizes TLS. When approved troubleshooting requires decryption, key custody and data handling need explicit controls in that environment. Our source package requires no decryption secrets. At Northstar, use a service configuration check, an authorized endpoint observation, and a bounded capture together when appropriate. Preserve the identity and limitations of each source. In an incident brief, say exactly which payload was readable and which remained unexamined. This gives the response owner enough information to choose a next check without confusing uncertainty with evidence of safety.

## S22 · ARP finds a local neighbor

Address Resolution Protocol, or ARP, helps a host discover the Ethernet address associated with an IPv4 address on its local link. A request can ask which station has a particular protocol address, and a reply supplies a hardware address. Hosts retain mappings in neighbor or ARP caches according to their implementation. When STAFF communicates with an off-subnet destination, the relevant local mapping is normally the gateway's IPv4 address. The remote server's IP remains in the packet. ARP's original mechanism does not cryptographically authenticate the identity making a claim. That design creates opportunities for false mappings when additional protections are absent. Read the sender hardware and protocol fields as well as the Ethernet header; they describe related but distinct layers. Our fixture shows explicit teaching mappings and replies. It does not cause any operating system to install those mappings because the file is only read offline.

## S23 · A false mapping changes a path

ARP poisoning attempts to persuade a recipient to associate a local IPv4 address with an inappropriate MAC address. If the recipient uses that mapping, subsequent frames can be sent toward the wrong station. A man-in-the-middle arrangement additionally depends on traffic reaching that station and being forwarded appropriately so the conversation can continue. A false reply alone does not prove successful bidirectional interception, content reading, or data theft. It can instead cause disruption, be ignored, or be rejected by controls. At Northstar, the synthetic ARP file contains two claims for the office gateway address using different source MAC addresses. This supports the observation that the supplied trace contains conflicting binding claims. It does not include a real cache change or actual forwarding path. To strengthen a live-lab conclusion, compare recipient state, switch-port evidence, approved gateway records, and relevant traffic on both sides within the same authorized interval.

## S24 · A change can be legitimate

A changed gateway mapping deserves investigation, but it can have legitimate explanations. A planned gateway replacement or high-availability event may change the observed association. A duplicate-address mistake may also produce conflicting claims without deliberate interception. At Northstar, compare the old and new MAC addresses with the approved gateway inventory, maintenance window, and switch observations. A device name inferred by an address database is not an authorization record. Repeated announcements can be relevant, but repetition alone does not establish malicious intent. Our fictional approval card deliberately leaves the change unconfirmed so the student must state a next check. A strong analysis records the observed addresses and timestamps, names the plausible explanations, and identifies evidence that would distinguish them. This approach supports a timely protective decision while preserving uncertainty about cause. Do not turn a training alert into a completed incident classification merely by giving it an alarming title.

## S25 · Verify ARP protections

Dynamic ARP Inspection, or DAI, can validate ARP traffic against trusted binding information and configured policy on supporting switches. DHCP snooping bindings often supply part of that information. Static hosts and special network arrangements need appropriate handling. Trusted ports are an important configuration boundary; trusting the wrong path can bypass intended inspection, while rejecting legitimate traffic can disrupt service. A defense therefore needs a documented topology, correct binding sources, a staged change, and validation. At Northstar, the proposed check compares a permitted gateway announcement with a known incorrect teaching claim in an isolated authorized lab. Verify the expected forwarding or rejection and the relevant logs. Our offline fixtures explain that decision but do not prove that a switch enforces DAI. Product support and exact commands vary by platform and release. Use the matching vendor documentation and preserve the actual device configuration with the result when a real lab is activated.

## S26 · Tools do not prove the result

Sniffing courses name tools that can observe ARP, generate address claims, or combine redirection with analysis. Wireshark can inspect stored ARP fields, and monitoring tools can track changes in observed mappings. Frameworks such as Ettercap and Bettercap include active network functions that require their own authorized environment. Knowing a tool name is useful for recognizing its role, but running a command successfully does not establish that a recipient changed its cache or that traffic was intercepted. In this package, the executable task is restricted to reading synthetic files. We examine the relevant fields without sending traffic or changing neighbor tables. At Northstar, a complete success criterion for any later lab would identify recipient state, traffic direction, control behavior, and retained evidence. That criterion should exist before choosing an active tool. It also prevents a familiar tool screenshot from being mistaken for proof of a particular network outcome.

## S27 · MAC spoofing changes a claim

MAC spoofing changes the link-layer address an interface presents. Legitimate operations, privacy features, virtual machines, and unauthorized impersonation can all involve address changes. The observed source address therefore needs context. A simple MAC allowlist can constrain a narrow environment, but it is not equivalent to strong user or device authentication. At Northstar, a new source address on an office port could indicate a replacement laptop, an additional virtual interface, or an unapproved device. Compare the port's expected role, endpoint inventory, authentication records, and approved change history. Do not infer a unique physical machine solely from a vendor prefix. Our fixtures use locally administered teaching addresses to avoid implying real hardware ownership. A defensive explanation should state what the control binds, how changes are authorized, and which observation verifies the expected state. That makes identity reasoning useful beyond memorizing a spoofing definition.

## S28 · MAC flooding targets learning

A MAC flooding technique attempts to stress a switch's address-learning resources by presenting many source addresses. The intended consequence is often broader forwarding of traffic whose destination no longer has a usable table entry. Actual behavior depends on the switch, resource partitioning, VLANs, configuration, and protection features. Do not teach that every modern switch becomes a hub when its table is full. A device may limit learning, drop traffic, enforce port security, or behave differently under load. At Northstar, the mechanism diagram shows the relationship between source learning and destination lookup, followed by the specific uncertainty about forwarding. There is no flooding generator in this package. A suitable later lab would measure table entries, platform counters, authorized test traffic, and availability within an isolated setup. A packet count alone cannot establish table exhaustion. The result must connect the attempted pressure to the actual forwarding behavior being claimed.

## S29 · Constrain access-port behavior

Port security can limit or constrain learned source addresses on supported access ports. The useful policy depends on what belongs on the port. A classroom port carrying a phone and a laptop may legitimately present more than one address. A virtualization host can present several. Choosing an arbitrary limit can create an outage without solving the intended threat. At Northstar, document the expected device roles and the configured violation action before proposing a change. Review counters, logs, and recovery behavior, then validate both accepted and rejected traffic in the permitted lab. Combine this with suitable authentication and inventory rather than treating MAC addresses as secret identities. A successful configuration command proves that the device accepted a setting, not that the entire defense works. The acceptance record should show the actual policy, a representative permitted use, a representative violation, and the resulting service and monitoring behavior.

## S30 · DHCP builds a lease

Dynamic Host Configuration Protocol helps a client obtain network configuration. In a common initial exchange, the client discovers available service, a server offers an address, the client requests a selection, and a server acknowledges it. The familiar DORA sequence is a teaching aid; renewals, relays, and other states can look different. Correlate the transaction identifier, client information, message type, and relevant options. A server identifier, router option, and DNS option play different roles. At Northstar, the authorized DHCP service is represented through the office gateway's module-specific role, and its proposed router and DNS settings are recorded explicitly. Our synthetic file includes a discovery and competing offers. It does not include a completed request and acknowledgment. Consequently, it cannot show which offer the client accepted or which configuration became active. That distinction matters when a suspicious offer suggests a possible redirection path.

## S31 · Starvation and rogue offers

DHCP starvation attempts to consume available leases or related resources so legitimate clients cannot obtain expected configuration. A rogue DHCP server supplies unauthorized configuration, potentially changing a client's gateway or resolver. These mechanisms can be combined, but observing one does not prove the other. A burst of discoveries alone does not establish that a pool was exhausted. Inspect server allocation records, available capacity, client results, and the timing of legitimate requests. Likewise, an unexpected offer does not prove the client accepted it. At Northstar, E03 presents two offers for one constructed transaction, including different router options. The strongest direct conclusion is a competition in the supplied exchange, with acceptance left open. A next check would identify the sending ports, authorized servers, and the client's selected configuration. Keep the operational effect, the policy violation, and the actor's intent as separate questions when writing the incident brief.

## S32 · DHCP snooping needs trust

DHCP snooping can distinguish trusted server-facing paths from untrusted client-facing paths and build binding information on supported switches. Correct trust placement helps prevent unauthorized server messages from entering through ordinary access ports. The learned database can also support other features such as DAI and IP Source Guard. Those dependencies mean that an incomplete or incorrect binding state can affect several controls. Rate limits may help constrain abuse, but values and enforcement behavior need platform-specific review and representative testing. At Northstar, map the approved server or relay path first, then mark the access ports and any static-host exceptions. Validate that a legitimate client obtains the correct lease and that an unauthorized teaching offer is handled as intended in an isolated lab. Preserve the binding table, relevant counters, and client configuration. Our source cards describe the proposed controls; they are not exports from a configured switch or proof of DHCP starvation prevention.

## S33 · VLAN hopping has conditions

VLAN hopping describes techniques that attempt to cross an intended Layer Two separation. One traditional mechanism abuses inappropriate trunk negotiation or port configuration. Another uses stacked tags under particular native-VLAN and forwarding conditions. These are not universal properties of every switched network, and the exact prerequisites matter. A double-tag illustration should show which device removes which tag, where forwarding occurs, and why the same path may not provide a symmetric return channel. Avoid implying that simply adding two tags defeats all VLAN controls. At Northstar, use the diagram to audit access-port roles, explicit trunk configuration, allowed VLANs, and native-VLAN choices against the intended design. We provide no attack transmission procedure. A defensive validation should test approved connectivity and isolation between named roles using the actual platform configuration. A VLAN number in a packet alone does not prove successful boundary crossing or access to another protected application.

## S34 · Make VLAN boundaries reviewable

A VLAN defense begins with an accurate port inventory. Identify which links must be trunks and which are ordinary access ports. Configure roles deliberately rather than relying on unnecessary negotiation. Review allowed VLANs, native-VLAN behavior, and the handling of unused ports according to the platform and design. A diagram saying that teachers and devices are separate is only a design statement. Configuration evidence shows the intended enforcement settings; observed connectivity tests show selected outcomes under stated conditions. Both are useful, and neither proves every possible route. At Northstar, define a permitted path and a path that should be isolated, then specify how an authorized operator would test them without affecting normal teaching. Preserve the source and destination roles, timing, expected result, and actual result. If routing or firewall policy intentionally connects the VLANs, account for that path before calling successful communication a VLAN-hopping event.

## S35 · STP protects a topology

Spanning Tree Protocol helps prevent loops in an Ethernet topology with redundant links. Devices exchange bridge protocol data units, or BPDUs, and select a forwarding topology using the relevant protocol rules. A device presenting inappropriate control information can affect root selection or topology behavior when protections and design boundaries permit it. This can change traffic paths or availability. It does not automatically decrypt traffic or prove a successful interception. At Northstar, show an expected root bridge and the access links where ordinary endpoints should not participate as switches. Then compare a reported topology change with maintenance records and actual device state. Our diagram is conceptual; the supplied packet fixtures do not contain a complete STP event. Any later lab must identify the protocol variant, platform, configuration, and measured change. The success claim should describe the actual selected root and port state rather than the mere presence of a BPDU.

## S36 · Guard the intended STP role

BPDU Guard and Root Guard address different expectations in a spanning-tree design. BPDU Guard is commonly used where a port should not receive BPDUs from an attached ordinary endpoint, while Root Guard constrains where a superior root advertisement should be accepted. Platform behavior and recovery settings require the matching vendor guide. These features are not interchangeable names for blocking every topology change. A legitimate uplink has different requirements from an edge access port. At Northstar, mark the intended role of each link before choosing a guard. Plan the availability effect, alerting, and recovery process, because enforcement may block or disable a path. Validate both normal redundancy behavior and the specific prohibited condition in an isolated authorized setup. A protection that prevents a test event but breaks the approved teaching network needs correction. Our source package supplies the reasoning and acceptance questions, not a completed switch experiment.

## S37 · DNS poisoning changes an answer

DNS connects a queried name and type to returned data under a hierarchy of zones, resolvers, and caches. A poisoning or spoofing technique attempts to cause acceptance of inappropriate data or to influence the response path. For analysis, correlate the question, transaction identifier, responding endpoint, timing, and returned records. Tools such as Bettercap include DNS-response spoofing functions. Generating a false local response and poisoning a recursive cache are distinct outcomes; both require acceptance evidence. No such tool function is activated here. A different IP address is not enough to establish poisoning. Load balancing, split DNS, legitimate updates, and caching can produce different answers. At Northstar, the synthetic file supplies two responses for the same constructed question and transaction, with different returned addresses. This establishes the conflicting supplied responses, while the client's acceptance and any later connection remain open. Compare the approved zone data and resolver logs to determine what should have been returned under those conditions. A packet's source IP is also a claim within the packet; it does not independently authenticate the sender.

## S38 · Protect DNS at the right layer

DNSSEC can provide origin authentication and integrity for signed DNS data when the validation chain and policy support it. It does not encrypt the DNS query or make every name signed. Encrypted DNS transports protect a communication path to a resolver, but they do not automatically establish that every returned answer is correct. Resolver trust, endpoint configuration, validation behavior, and the authoritative zone still matter. At Northstar, ask which question a proposed control answers. Does it protect the path, validate signed data, limit authorized resolvers, or detect an unexpected endpoint setting? These can complement one another without being equivalent. The fixture's conflicting replies are deliberately simple teaching records; no DNSSEC validation run or encrypted DNS session is claimed. A later verification should record the chosen resolver, relevant policy, response validation state, expected record, and actual client behavior. Preserve the evidence behind the conclusion instead of relying on a security-feature label.

## S39 · Passive and active sniffing

Passive sniffing observes traffic available at a collection point without deliberately changing another station's path. Active sniffing techniques manipulate network behavior to gain visibility or influence delivery. Examples discussed in the course include false address claims and other local-network changes. These categories describe mechanisms, not whether an activity is authorized. Even passive collection can expose sensitive information, while a carefully bounded active exercise may be permitted in a dedicated lab. At Northstar, our executable workflow remains offline and read-only. The animation can show how a path might change without causing that change on a real network. When reviewing a report, ask exactly what the operator did and what the evidence shows. A packet analyzer screenshot may be passive observation of an already supplied file, not proof that the operator performed the active technique illustrated beside it. Keep the action, its permission, and its measured result in separate fields.

## S40 · Detect suspicious collection

Detecting a sniffer is challenging because a collector may transmit very little or nothing while it observes. A remote probe can sometimes reveal particular implementation behavior, but a negative result cannot rule out every passive collector. Some traditional promiscuous-detection techniques rely on how a host responds to specially addressed traffic. Their results depend on operating system, driver, protocol stack, topology, and filtering behavior. Nmap names one such local-Ethernet test sniffer-detect and classifies it as intrusive. We discuss its role without executing a probe. At Northstar, use authorized endpoint inspection, interface state, inventory, and network-control evidence where available. An interface in promiscuous mode may belong to legitimate monitoring, virtualization, or troubleshooting. The state needs an approved purpose and owner before it becomes an incident conclusion. Conversely, no suspicious response to one probe does not establish a clean network. ## S41 · Choose tools by their job

Wireshark provides interactive protocol inspection and display filtering. Tcpdump provides command-line capture and offline reading with libpcap expressions. Binding monitors can report changes in observed address relationships, while switch telemetry can describe ports and control behavior. Tool selection should follow the question. A conversation count does not answer whether an ARP change was approved, and a binding alert does not show which application accepted a login. At Northstar, the build environment has tcpdump, so the package preserves actual offline tcpdump checks. It does not invent a TShark execution receipt when that executable is unavailable. ## S42 · False positives and false negatives

A false positive occurs when a detection interprets benign activity as the harmful condition of interest. A false negative occurs when the relevant harmful condition is present but the detection misses it. Define the detection target before using these labels. An accurate alert that a MAC mapping changed can be followed by an incorrect inference that an attacker caused it. The observation may be true even when the incident classification is false. A missing alert can reflect a quiet network or inadequate coverage. At Northstar, compare the proposed ARP, DHCP, and DNS interpretations with maintenance records, client state, and collection coverage. Tune a rule using the specific benign context while preserving the intended harmful-condition coverage. Broadly disabling a noisy sensor removes evidence as well as noise. A useful validation records representative expected and unexpected cases, the actual observed results, and the remaining limits of the test.

## S49 · Choose layered defenses
